项目背景：传统“聊天式” AI 产品容易把状态、权限、失败恢复和上下文交接藏在对话里，难以追踪和复用。我把它拆成一个本地工作台，让模型负责候选输出，项目自身负责运行状态、审批、工具和产物。

核心工作：设计 Project / Bot / Run / RunEvent / Handoff / Approval / Artifact / Memory 契约；以 SQLite 保存运行事实；实现 Product Builder 的澄清、规划、结构化交接、评测和用户确认；建立 Provider 与 ExecutionAgent 的身份和计费来源边界；补齐只读工具、路径与符号链接防越权、命令白名单、脱敏、取消、幂等和恢复。

结果：形成可从 Git 复现的本地 Web/Electron 交付版；Fixture 无 Key 可运行；真实 DeepSeek 只读 Tool Loop 和 Codex CLI 能力探针有独立回执；全量工程测试 105/105 通过。模型质量、多 Bot 提效、真人效率和签名发布仍单独标为未验证。

二、你要怎么讲这个项目

30 秒版本

我做的是一个本地优先的 Agent 工作台。它不是把几个 Prompt 串起来，而是把项目、Bot、运行状态、工具权限、审批和产物放进一个可追踪的控制面。用户输入一个产品想法后，Product Builder 会按结构化流程推进，模型只负责生成候选，系统自己负责状态、回放、失败恢复和权限边界。现在已经有 Web/Electron 本地交付版，Fixture 流程可直接运行，真实 Provider 也有独立适配和回执。

2 分钟版本

我做这个项目，是因为普通 AI 对话在短任务里很方便，但长任务会出现三个问题：第一，状态藏在聊天里，换窗口或中断后很难恢复；第二，模型到底读了什么、调用了什么工具、为什么能发布，通常不透明；第三，模型通道和本地执行混在一起，容易把 API、订阅和本地权限混淆。

所以我把它设计成一个本地 control plane。核心状态由项目自己的 TypeScript core 和 SQLite 控制，每次 Run 都有明确状态和 append-only RunEvent。Provider 只是模型或执行桥，不能直接成为业务事实源。工具调用要经过权限策略，危险动作逐次审批，产物只有通过固定检查并经过相应审批才能晋级。

第一个可见流程是 Product Builder：想法先澄清未知项，再规划、生成结构化产物、评测、冲突检查，最后由用户确认。现在我证明的是这条控制链路可运行、可回放、可恢复；没有把 Fixture 或单次真实模型调用说成模型质量或生产力证明。

5 分钟版本的顺序

  1. 先说问题：长任务需要状态、权限、恢复和证据，而不是只要一段文本。
  2. 再说核心判断：模型不是系统事实源；模型输出是候选，项目控制面才记录状态和决定能否继续。
  3. 展示主流程：输入想法 → 澄清未知项 → 规划 → Bot 交接 → 评测 → 用户确认 → Artifact。
  4. 展示一条事件：run.created → run.started → provider.event → tool.invoked → tool.completed → artifact.created → run.succeeded。
  5. 讲安全边界：只读、工作区写入、完全访问分档；外发、删除、敏感路径、生产配置、支付/发布和凭据读取始终逐次审批。
  6. 主动讲边界：当前证明了工程控制面和本地交付，不证明多 Bot 一定更快、模型一定更好或真人一定节省时间。

四层结构

层负责什么你面试时怎么解释
Core（核心契约）类型、状态机、事件投影、幂等把“运行发生了什么”定义成可以回放的契约。
Control plane（控制面）本地 HTTP Server、SQLite、审批、Artifact、恢复把模型候选变成受约束的运行流程。
Adapter（适配层）Fixture、DeepSeek、Codex CLI、ToolRuntime换模型或执行桥，不换业务状态机；身份和计费来源分开记录。
Web / Electron同一套 Web UI 的浏览器和桌面入口桌面只是壳，不复制第二套业务逻辑。

一次运行发生什么

1. 创建 Run，状态 queued → running
2. 记录目标、项目范围、Bot 和 Provider 身份
3. 模型提出结构化结果或工具调用
4. Tool Policy 检查路径、命令、权限和审批
5. 每个动作追加 RunEvent 和 receipt（回执）
6. 产物写入 SQLite，失败也留下可诊断事件
7. 需要时生成 ContextSnapshot，重启后恢复同一逻辑 Run
8. 高风险候选停在 waiting_user，不能自动发布

五、面试官可能怎么问

回答顺序：先给判断，再给项目里的具体机制，最后主动说验证边界。不要把下面的文字机械背成目录。

1. 这不就是几个 Prompt 串起来吗？

如果只是 Prompt 串联，我同意它没有太大产品价值。这个项目的核心是控制复杂任务：谁负责、读什么、能不能调用工具、失败如何恢复、产物能不能发布。Prompt 只是产生候选，状态机、权限策略、RunEvent 和审批才决定流程是否继续。
证据：Core 状态机、ToolRuntime policy、approval route、RunEvent replay。

2. 为什么不直接用一个强模型？

不一定需要多个 Bot。不同职责只有在输入、评价标准或权限明显不同，并且固定任务证明收益时才值得拆开。当前我先把结构化单流程和专门角色做成可比较路径，没有把“多 Bot”当成天然优势。
边界：当前没有真人效率或多 Bot 质量优势证据。

3. 你怎么避免模型胡编？

我把外部事实、结构化输出和评测分开处理：需要来源的结果必须带 Source；进入正式 Artifact 前要过 Schema 和固定检查；未知项必须保留，不能被模型补成事实；高风险候选停在审批边界。模型自评只能作为反馈，不能单独当作产品质量证明。
证据：Product Builder unknowns、Artifact release gate、RSI evaluation。

4. DeepSeek、Codex 和 Fixture 分别是什么？

Fixture 是无 Key 的确定性控制面演示；DeepSeek 是 ModelProvider（模型提供方），负责模型响应；Codex CLI 是 ExecutionAgent（执行代理），负责在本机按权限执行。三者的认证方式、计费来源、模型身份和 mock 标记分开记录，不能把订阅额度写成 API 额度。
证据：ProviderIdentity、provider receipt、Codex capability probe。

5. 你为什么选 SQLite？

这是本地优先产品，第一阶段更需要事务、一致性、重启回读和单机可复现，而不是先引入云端多用户复杂度。SQLite 作为运行时唯一事实源，JSONL 只承担导出、演示和灾备；Web 和 Electron 共享同一 control plane。
证据：persistence adapter、schema migration、reopen/recovery tests。

6. 上下文窗口满了怎么办？

不把整段聊天当唯一状态。系统按阈值生成带 hash 的 ContextSnapshot，保留长期事实、决策、未知项、来源、审批和最近事件尾部；恢复时开启新的 segment，继续同一逻辑 Run。事件缺口、哈希不一致或跨项目恢复会失败。
边界：这验证的是项目恢复包，不等于证明 Codex 内部原生压缩或缓存命中。

7. 你的 Tool Calling 怎么保证安全？

工具调用先过结构化参数校验，再过项目范围、路径、符号链接、命令白名单和权限层级检查。只读工具可以直接执行；写入、删除、外发、敏感路径和生产动作逐次审批。审计事件只记录必要元数据，不把文件正文或凭据写进回执。
证据：sandbox、ToolRuntime、approval 和脱敏测试。

8. 你怎么证明它有效？

我把“工程能跑”“模型质量”“真人提效”分成三道门。当前已完成工程控制面、固定任务、Provider 边界、失败恢复、Web/Electron 和本地交付验证；固定记忆基准里混合召回排序更好，但还没有把它升级成真实生产提效结论。下一步要用非敏感真实项目和固定问题做对照。
证据：RUN_STATE、validation/、docs/DELIVERY-REPORT-V0.1.md。

9. RSI（自动评测和改进）会不会自己乱改？

不会默认自我扩张。RSI 只能生成候选、记录评测和反馈；低风险 Prompt 候选也有固定检查和可回滚记录；Provider、Tool Policy、代码、Bot 和 Routine 等高风险目标必须逐次审批。当前混合记忆策略也是单次可选，不会自动改全局默认。
证据：ImprovementProposal、approval boundary、memory strategy validation。

10. 你本人到底做了什么？

我负责产品问题定义、边界取舍、领域对象和工作流设计、Provider/权限/评测契约、验证标准和交付路线，并用 Codex 把方案落成可运行代码，再通过测试和回执核对结果。面试时不把“我设计了”和“代码由 AI 协助完成”混在一起说。
口径：强调产品判断、架构取舍、验收和风险控制；不要冒充纯手写工程实现。

11. 这个项目最大的风险是什么？

最大的风险是控制面做得很完整，但真实模型质量和真实生产力还没有被充分证明。所以我把 Fixture、真实 Provider、固定评测和真人使用分开记录；当前交付目标是本地可运行和可追踪，后续再用固定真实任务决定哪些能力值得默认启用。

12. 如果重做一次，你会先改什么？

我会先做一个真实、非敏感任务的单次模型基线，然后只增加一个可测的增量，例如策略选择、工具调用或恢复包，再比较质量、延迟、成本和人工修改量。只有增量在固定门槛下成立，才继续扩大 Agent 或自动化范围。
