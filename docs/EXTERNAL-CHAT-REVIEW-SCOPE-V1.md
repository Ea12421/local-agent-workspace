# 网页 Chat AI 外部评审重点范围 v1

## 使用目的

这份清单用于约束网页 Chat AI 的评审范围。目标是让它产出能改变项目质量和实施顺序的判断，而不是输出一篇泛泛的 Agent 平台百科。

推荐流程：

```text
盲评设计包
→ 按本清单重点审查
→ 知情复核当前实现
→ 主控核验和落盘
```

## P0：必须优先回答

### 1. 产品核心价值和最小闭环

让它判断：

- 用户真正反复使用的任务是什么；
- 这个产品解决的是“生成内容”还是“持续推进任务”；
- Product Builder 是否只是示例，还是第一条真正可复用的 Workflow；
- 最小可交付闭环是什么；
- 哪些功能看起来厉害但对第一次使用没有帮助。

要求输出：

- 一个最小用户旅程；
- 一次运行必须留下的状态和产物；
- 明确的交付标准；
- 不能进入第一阶段的功能清单。

### 2. 长任务控制和恢复

让它重点判断：

- Run、Segment、ContextSnapshot、Handoff、Approval 的职责是否清楚；
- 模型限额、网络失败、超时、用户关闭窗口后如何继续；
- 哪些状态必须持久化；
- 哪些内容应该压缩，哪些内容不能丢；
- 恢复后如何避免重复工具调用、重复 Artifact 和重复外发；
- 如何证明“恢复成功”，而不是只证明进程重新启动。

这是当前最重要的稳定性问题，因为用户已经遇到模型限额导致任务被打断。

### 3. Provider 边界和可替换性

让它明确区分：

- 订阅型 Execution Agent；
- API 型 Model Provider；
- OpenAI-compatible API；
- 本地模型；
- Fixture。

要求它回答：

- 哪些能力由 Control Plane 负责；
- 哪些能力必须由 Adapter 负责；
- capability probe 应该检查什么；
- 什么时候可以说“换 Provider 可运行”；
- 认证、计费、额度和模型身份如何避免混淆。

不要让它只比较框架名称。要它比较真实行为：消息、streaming、tool calling、structured output、reasoning、usage、cache、cancel、resume。

### 4. Tool Loop 的真实闭环

让它从一条完整调用开始推导：

```text
模型提出调用
→ 参数校验
→ 权限判断
→ 审批
→ ToolRuntime
→ receipt
→ 工具结果回传
→ 模型继续
```

必须覆盖：

- 成功；
- 越权；
- 审批拒绝；
- 超时；
- 取消；
- 重试；
- 重复提交；
- 中断恢复；
- 工具结果太大；
- 工具调用循环过深。

要求它指出当前哪些只是权限和工具执行能力，哪些还没有形成模型到工具的闭环。

## P1：决定长期成本和维护性

### 5. Prompt Cache、Usage 和长任务成本

让它不要把 Prompt Cache 当成必然存在的能力，而是判断：

- 哪些内容稳定且值得缓存；
- cache key 由什么组成；
- 工具 Schema、权限、项目状态改变时如何失效；
- Provider 不提供命中指标时如何降级；
- 哪些成本能真实记录，哪些只能估算；
- 多 Bot 是否只是复制上下文和增加延迟；
- 重试和压缩本身是否会增加成本。

要求输出一张表：

```text
机制 | 解决的问题 | 真实成本 | 需要 Provider 支持吗 | 当前优先级 | 验收方法
```

### 6. Single Bot、Workflow 和 Multi Bot 的取舍

让它不要默认“多 Agent 更高级”，而是用任务拆分和评价标准判断：

- 单 Bot 能否完成；
- 什么时候需要结构化 Workflow；
- 什么时候才值得多个 Bot；
- 多 Bot 带来的质量增益如何证明；
- 延迟和成本上限是什么；
- 失败时如何定位是哪个 Bot 的问题。

它必须给出默认策略：

```text
默认路径是什么
何时升级到多 Bot
什么证据会让我们退回单 Bot
```

### 7. 可观察性和证据

让它设计最少但够用的观测字段：

- Run/Segment；
- Provider identity；
- authMode/billingSource；
- input/output usage；
- cache status；
- tool calls；
- approvals；
- retries；
- duration；
- error code；
- artifact/source refs。

要求它区分：

- 工程通过；
- 真实模型通道通过；
- 现实任务通过；
- 用户愿意重复使用。

## P2：只有在 P0/P1 清楚后再看

### 8. Skill、Workflow、Bot 的长期模型

让它回答：

- 一个 Skill 什么时候应该封装成 Bot；
- Skill、Workflow、Bot、Agent 的边界；
- Skill 版本如何发布和回滚；
- 自优化是否真的需要；
- 如何防止自动生成 Bot 无限递归或提升权限。

### 9. Web、Electron 和安装复现

只审查：

- 本地 Server 归属是否明确；
- Web/Electron 是否共享同一业务逻辑；
- 关闭、重启、端口冲突是否可诊断；
- GitHub 下载后能否复现。

不要让它把主要精力放在图标、颜色和视觉细节上。

## 本轮明确不让它主导的内容

- UI 视觉风格；
- 应用图标；
- 云端多用户；
- 自动发布和外发；
- 任意 Shell；
- 无人工审批的 Bot 自我扩张；
- 现在就引入大型 Agent 框架；
- 没有证据的多 Bot 宣传；
- 没有 Key 时的 DeepSeek 效果结论。

## 要求外部 AI 最后给出的结果

1. P0/P1/P2 优先级表；
2. 当前项目应保留、重做、后置的部分；
3. 一个唯一主路线；
4. 下一步只做一个工程单元；
5. 每个阶段的测试和停止条件；
6. 可能推翻当前方向的证据；
7. 它认为当前方案最薄弱的三个点。
