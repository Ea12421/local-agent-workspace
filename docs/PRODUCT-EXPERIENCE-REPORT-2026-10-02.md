# Local Agent Workspace 产品体验审计 v1

## 审计范围

- 目标：Local Agent Workspace Web/Electron 工作台
- 模式：Operate（用户需要完成任务，而不是只浏览页面）
- 入口：工作台概览、Bots、运行记录、项目产物、新建运行、审批卡片
- 依据：当前源码、Product Contract、Product Builder Workflow、User Guide，以及 2026-10-02 Computer Use 的安装版视觉/可访问性检查
- 结论边界：这是界面与使用路径审计，不代表真实模型质量已经验证

## 设计健康分

| 启发式原则 | 分数 | 主要问题 |
|---|---:|---|
| 系统状态可见 | 3/4 | 状态、进度、时间线清楚，但运行徽章固定为 1，完成/失败状态仍可能显示运行中的视觉 |
| 贴近用户语言 | 2/4 | Provider、Fixture、receipt、ToolRuntime 等术语对首次用户负担较大 |
| 用户控制与自由 | 2/4 | 有取消弹窗、批准、重试，但没有真正取消运行；“修改问题”实际是重试 |
| 一致性与标准 | 2/4 | 卡片和颜色统一，但大量未实现控件仍像可点击功能 |
| 错误预防 | 2/4 | 只读范围和 Provider 说明有防护；审批选项不是可变的真实选择控件 |
| 识别而非回忆 | 2/4 | 主要页面可见，但六种执行入口需要用户先理解系统架构 |
| 灵活与效率 | 1/4 | 搜索、筛选、视图切换、Provider 设置均未实现 |
| 美学与极简 | 2/4 | 结构清楚，但小字号、浅灰文字和首屏模块过多影响阅读 |
| 错误恢复 | 2/4 | 有失败卡片和 Toast，但错误信息缺少下一步、请求 ID 和可靠重试入口 |
| 帮助与文档 | 1/4 | 帮助按钮没有行为，用户需要离开应用阅读文档 |
| **总分** | **19/40** | **工程 Alpha 可用；面向非技术用户仍需一轮体验修正** |

## 设计特异性判断

当前视觉属于典型的轻量 SaaS/Admin Dashboard：左侧导航、紫色主色、指标卡和卡片网格。换成项目管理后台或客服后台也可以复用，产品专属性偏弱。

真正有辨识度的内容已经存在：本地优先、只读安全范围、Run 时间线、审批边界、Provider 回执、可恢复和可追溯。问题是这些价值多数被放在“技术详情”或术语里，没有成为首屏主叙事。

## 做得好的地方

1. “只读取当前项目内容，不会修改文件”把安全边界直接展示出来，能建立信任。
2. Run、Handoff、Approval、Artifact 和来源形成可追踪链路，这是产品区别于普通聊天窗口的核心。
3. 页面结构简单，概览、Bots、运行记录、项目产物四个入口容易理解，适合继续扩展。

## 最高优先级问题

### [P0] 审批选项看起来可以选，实际不能选

证据：apps/web/src/App.tsx 的 ApprovalCard 使用静态 label 和自绘 radio，没有真实 input、状态或点击切换。

影响：用户可能以为自己选择了另一个目标用户，但系统仍提交默认选项。这会使审批记录失真，是权限和产品决策问题。

修复：审批选项从真实 Approval 数据读取；使用受控选择状态；提交前显示“你将批准什么”摘要；审批事件记录最终选择的值；没有真实选项时不要渲染可选择的假选项。

建议命令：$impeccable harden + $impeccable clarify

### [P1] 移动端主导航失效

证据：移动端隐藏 sidebar，但 mobile-menu 只有图标，没有展开行为。

影响：手机或窄窗口无法进入 Bots、运行记录和项目产物。

修复：实现移动抽屉；支持 Escape 和点击外部关闭；增加 aria-expanded；保持当前页面高亮。

建议命令：$impeccable adapt

### [P1] 新建运行让用户先理解技术架构

证据：新建运行一次列出 Fixture、ToolRuntime、文件读取、Git、Codex 等多个入口。

影响：第一次使用者不知道应该选什么，也不知道哪个会调用真实模型、哪个会读取文件、哪个会产生费用。

修复：默认只显示“开始一次本地演示”和“检查当前项目”两条路径；其余入口放进“高级诊断”，并说明用途、是否真实模型、是否读取文件、是否产生费用、是否会修改文件。

建议命令：$impeccable distill + $impeccable clarify

### [P1] 失败和恢复路径不够具体

证据：初始 API 失败可能停留在载入页；失败提示容易退化为“未知错误”；没有取消运行和明确恢复操作。

影响：用户不知道是网络、权限、Provider 还是任务本身失败，也不知道下一步该做什么。

修复：加载失败显示“重试 / 使用本地演示”；错误卡显示错误类型、Run ID、是否可重试；运行中提供取消；失败后提供“重试当前 Run”和“修改目标后重试”两个不同动作；失败事件显示失败图标，不继续显示 spinner。

建议命令：$impeccable harden

### [P2] 未实现控件过多，像产品坏了

观察到：新建项目、搜索、时间筛选、视图切换、Provider 设置都显示为后续开放，帮助按钮没有行为。

修复：首版要么隐藏，要么统一放入“即将开放”区域，不要把它们放在主要操作区伪装成当前功能。

建议命令：$impeccable distill

### [P2] 首屏信息太多，技术信息和用户信息混在一起

概览首屏同时出现指标卡、安全范围、澄清、计划、最近运行、当前运行、Provider、Bots、Artifact。

修复：首屏只保留当前任务、当前需要用户做什么、已经产出了什么、下一步是什么。workspacePath、receipt、缓存、原始响应等放到可展开的“运行证据”抽屉中。

建议命令：$impeccable layout + $impeccable distill

## 用户人物风险

- 首次使用者：看到六个执行入口和大量技术术语，不知道如何开始；帮助按钮没有响应，失败后没有明确恢复路径。
- 高频使用者：没有搜索、筛选、快捷键、最近目标模板，也不能取消正在运行的任务；重复测试需要手动重新输入。
- 隐私敏感用户：安全范围卡片做得好，但 workspacePath、费用、缓存和原始响应都藏在技术详情里；审批选择又不可真实切换，授权可信度不足。

## 当前体验路径中的主要断点

打开应用 → 能进入工作台
查看当前项目 → 能看到只读边界
开始运行 → 入口太多，缺推荐路径
等待运行 → 时间线有，但状态语义不总是准确
用户审批 → 选择控件是假交互
查看产物 → 能看到文件和来源
失败恢复 → 有错误提示，但缺明确下一步
移动端使用 → 导航不可用

## 三条后续方向的判断

### 方向一：先做真实使用体验

优先级最高。先修 P0/P1：审批真实选择、失败恢复、运行状态、移动导航、新建运行入口。

### 方向二：对照原始设计和 SPEC

第二优先级。对照产品契约检查每个用户动作是否有真实状态、每个审批是否有真实数据、每个 Artifact 是否能解释对用户有什么用、Fixture/Codex/DeepSeek 的真实程度是否清楚。

### 方向三：视觉升级

第三优先级。当前不需要推倒重做。应保留现有结构，先放大中文正文和状态文字、提高浅灰文字对比度、把“本地、可恢复、可审计”变成视觉主线、减少首屏卡片、统一禁用/加载/失败状态，再升级 A 图标。

## 推荐迭代顺序

P0 审批真实交互
→ P1 新建运行简化 + 状态/错误恢复
→ P1 移动导航
→ P2 首屏信息分层
→ P2 清理未实现控件
→ 视觉对比度和字号
→ 再做 Skill/Routine/自动迭代

当前不建议先做更多 Bot、更复杂的多 Agent 编排、后台自动任务或大规模视觉重做。这些会把现有可用性问题藏在更多功能下面。

## 需要后续决定的问题

1. 首屏第一目标是“开始一次运行”，还是“审计当前运行”？
2. 第一阶段面向普通 AI Builder，还是只面向懂 Agent 的面试官？
3. 六个执行入口是正式产品能力，还是当前调试入口？
4. 是否把“本地、可恢复、可审计”作为主视觉和主文案？

## 2026-10-02 实施回归

本轮已完成的内部修复：

- 审批卡片移除无法提交的业务单选项，改为展示真实的审批动作、权限等级和当前受控范围；目标用户仍通过澄清契约处理。
- 失败事件映射为失败状态并使用失败标记；已完成运行不再显示为“当前运行”。
- 首次加载、审批/重试、刷新和运行入口失败都会给出可见提示或重试路径；帮助按钮提供本地演示、运行方式和审批边界说明。
- 移动导航具备打开、关闭、菜单切换和 Escape 关闭逻辑；未实现控件改为明确的“后续开放”说明。
- 新建运行将主要路径与高级诊断分组，并保留每种方式的读取、费用和真实性说明。

验证证据：`validation/ux-hardening-v1-2026-10-02.json`。这轮只验证本地控制面和界面行为；没有把 Fixture 结果升级为真实模型质量，也没有声称真实 DeepSeek/Codex 业务效果已经验证。
